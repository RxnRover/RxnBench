# Changelog

All notable changes to Rxn Bench are recorded here. Packages are currently pre-release (`0.1.0`, unversioned), so entries are dated rather than tied to semver releases until the first cut.

Format: newest entry first, one bullet per change, prefixed with the area it touches (`gantry`, `ph`, `client`, `frontend`, `docs`, etc.).

## Unreleased

- frontend: add a `windows-latest` GitHub Actions workflow (`.github/workflows/windows-installer.yml`) that builds the Windows desktop installer and uploads it as an artifact - so the `.exe` can be produced from a Linux dev machine (PyInstaller can't cross-compile and Inno Setup's `iscc` is Windows-only, so it must run on Windows). Triggers on tags (`v*`) and manual dispatch; installs Inno Setup (`choco install innosetup`), runs the PyInstaller onedir build + `copy_device_plugins.py` + `iscc packaging/installer.iss` (invoking the underlying commands directly since Windows runners lack `make`), uploads `Rxn-Bench-Setup-<version>.exe` as a workflow artifact, and - on version-tag builds - also attaches it to that tag's **GitHub Release** (`softprops/action-gh-release`, `contents: write`) so it has a permanent, repo-visible download URL; tags with a pre-release suffix (e.g. `v0.1.0-rc1`) are marked prerelease so they don't become "Latest". Version is read from `pyproject.toml` via `tomllib` (cross-platform, no grep/sed); the frozen self-test runs `continue-on-error` since Windows Qt-platform-plugin bundling is still unverified. Separate from `ci.yml` (untouched). **First real run (2026-07-13) confirmed the Windows PyInstaller build works** (onedir + plugin staging + frozen self-test all passed on the runner); the `iscc` step initially failed on a Git-Bash/MSYS quirk that rewrote the `/DMyAppVersion=` option into a path - fixed by running that step in PowerShell. Re-run pending to confirm the installer `.exe` builds + publishes end-to-end (2026-07-13).
- gantry: bump the Gantry SiLA feature from **v0 to v1** (`edu.iastate.ames/rxnbench/Gantry/v1`), matching `PHSensor/v1`/`Camera/v1`. `feature.py`'s `version` was already `"1.0"` (→ v1); this completes the bump across the wire artifacts that were still `v0`: `gen_proto.py`'s gantry manifest package, the regenerated `motion_platform.proto` + `_pb2.py`, `connection_spec.yaml`'s package, the regenerated `generated_connection.py` `_PKG`, and `widget.FEATURE_ID`. `FEATURE_FRAGMENTS` stays version-agnostic (`"Gantry"`), so plugin discovery is unaffected; `check-proto` and `check-connections` pass. **Deploy note:** frontend and backend must go together — a v1 frontend's gRPC method paths (`…gantry.v1.Gantry/…`) won't match a v0 backend, and vice versa (2026-07-13).
- gantry: visualize the X-gantry crossbar in the workspace viewer's X/Z and Y/Z side views under "show more details". `GetLimits`' pipe-delimited string gained two trailing fields (`…|crossbar_clearance_above_tip|crossbar_y_thickness`, empty when the crossbar model is unconfigured) — still one SString, so no proto change; the frontend parses 7 or 9 fields (forward/backward wire-compatible). The two values thread through `limits_updated` (now carrying them as `object` = float|None) and `set_limits` into `DeckSideViewCanvas`, which draws the bar underside at `current tip Z + clearance` — a full-X line in the X/Z view, a Y-thickness band at the carriage's Y in the Y/Z view — only when `show_details` is on and the geometry is set. Tests: backend `get_limits` 9-field format + crossbar-present; frontend `set_limits` storage + render smoke in both projections (2026-07-13).
- gantry: X-gantry crossbar collision check (opt-in). The carriage rides on a horizontal crossbar spanning X at the carriage's Y; lowering Z brings the whole bar down, so descending to engage a *low* plate while a *taller* plate shares that Y-row can drive the bar into the tall plate even though the tip is clear (the intra-plate optimization above makes this more likely). New `MachineConfig.crossbar_clearance_above_tip_mm` (crossbar underside height above the tip, in the workspace Z frame) + `crossbar_y_thickness_mm` (the bar's Y extent) model it; both must be set or the check is inert and motion is unchanged. `WorkspaceManager.max_top_in_y_band` finds the tallest plate sharing the bar's Y band, and `GantryController` refuses a well move whose docking would already sink the bar into a taller same-row plate, and refuses an `engage_tool` descent that would (behavior chosen: auto-raise travel where possible, else refuse). Wired from `MachineConfig` through `server.py`. Verified: refuse-on-dock, allow when the tall plate is a different Y-row, refuse-on-engage, and fully inert when unconfigured. Activation needs the operator's crossbar measurements in `~/.rxn_bench/machine.yaml` (2026-07-13).
- gantry: intra-plate travel optimization - moving between wells of the *same* plate no longer rises all the way to the full-deck safe-clearance height (the max over every plate on the deck), it now travels at just that one plate's own uniform top surface + padding, cutting the raise/lower time on multi-well scans (a tall beaker sharing the deck used to force every hop between two shallow-plate wells up to the beaker's height). `GantryController` gained `_plate_clearance_z(plate_id)` (clears one plate, still keeps the tip above z_min, deliberately skips the bare-carriage comfort floor) and decides "same plate" from the *actual current tip position* vs. the target plate's footprint (`WorkspaceManager.plate_footprint_bounds`, exact for the supported 0/90° orientations since the rectangle stays axis-aligned) - stateless, so a manual jog or cross-plate hop can't fool it into travelling too low; any inability to determine position falls back to the full deck clearance. Plain `move_to` (no plate context) and cross-plate hops keep the full clearance. `move_to`'s offset-compensated body was extracted into a shared `_travel_to(...)` that takes an explicit clearance. Verified with new tests (first move, same-plate lower raise, cross-plate full raise, plain-move full raise). Note: this optimization does NOT yet account for the X-gantry crossbar sweeping over a taller plate in the same Y-row while the carriage stays within a short plate - that collision check is separate, tracked as a gap (2026-07-13).
- gantry: make the shared deck/"workplate" thickness a first-class, configurable part of workspace Z geometry, separate from per-plate footprint. A well's opening Z is now `deck_height_mm + plate.origin.z + labware plate_height_mm` - three layers, each configurable at its natural scope: `deck_height_mm` (new, workspace-level) is the shared base plate's top height above Z=0 (the bed), `origin.z` (per-plate) is now that plate's own footprint/mount height *above the deck*, and `plate_height_mm` (labware) stays the plate's own height. Previously the shared deck thickness had to be baked into every plate's `origin.z`, so swapping to a different-thickness deck meant editing every plate; now it's one line. Fully backward compatible: `deck_height_mm` defaults to 0, so any workspace YAML without it behaves exactly as before (each plate's `origin.z` alone = resting-surface height above Z=0). Threaded through `WorkspaceConfig` (field + `from_dict`/`to_yaml_string` round-trip), `WorkspaceManager.resolve_well`/`max_labware_top_z`, and - independently, respecting the no-backend-import rule - the frontend's `workspace_loader.resolve_reference_plate_height` (so the calibration-reference-well Z-reference lands on the plate's real top even when the deck is raised) and the X/Z-Y/Z side views (plates drawn on top of the deck; the Z=0 line relabelled "Z=0 (bed)" with a "deck top" line when raised). `ph_experiment-1.yaml` gained the field (default 0) with a comment explaining the model. New tests for the Z composition, backward-compat default, and YAML round-trip (backend + frontend). Also fixed 5 pre-existing `test_controller.py` failures found along the way (unrelated to this change - proven by stashing it): they hardcoded `96_well_standard`'s `plate_height_mm=39`/`24_well_standard`'s shallow well depth, both since re-measured in the labware YAML, violating the repo's own "never hardcode plate dimensions outside labware/*.yaml" rule - rewired to derive from `PlateGeometry` and to set a deliberately-too-deep `z_engage` rather than assume a specific plate is shallow (2026-07-13).
- frontend: fix the Experiment Runner opening a second UI (and running nothing) instead of running the selected script in a packaged build. `_ScriptRunner` launched scripts with `subprocess.Popen([sys.executable, script])`; in a PyInstaller build `sys.executable` is the frozen GUI app, not a Python interpreter, so it re-launched the app (the script path ignored as `argv[1]`) - a new window, no script. Fixed by making the runner frozen-aware (`_ScriptRunner._build_command`): when `sys.frozen`, it re-execs the bundle with `RXN_BENCH_UI_RUN_SCRIPT=<path>` set instead of passing the script as an argument; the packaging entrypoint (`entrypoint.py`) gained a matching mode that `runpy.run_path(...)`s the script as `__main__` with line-buffered stdout (the frozen bundle already ships `rxn_bench_client` + grpc, so bench-driving scripts run directly). Source/dev behavior (`[sys.executable, script]` with real Python) is unchanged, as is the SIGINT-based clean Stop (KeyboardInterrupt still propagates into the script's `with RxnBenchClient()` cleanup). New `tests/test_experiment_runner_command.py` asserts the frozen path never hands the script to the exe as an argument. Takes effect once the frontend executable is rebuilt (`make dist`) - the fix lives in code baked into the exe (2026-07-13).
- ph: add a UART/serial driver for the Atlas EZO-pH circuit alongside the existing I2C one - the bench probe is wired to the Raspberry Pi's TX/RX (UART), not I2C, and EZO circuits ship in UART mode by default (a fresh circuit answers nothing on I2C until manually switched, which is the `Errno 121 Remote I/O error` the I2C path was hitting). The transport-agnostic EZO command set (`read_ph`, `calibrate_*`, `get_slope`, ...) was extracted into a shared `ezo_commands.EZOCommandSet` mixin so the two drivers - `AtlasScientificEZO` (I2C, keeps the status-byte parsing + `set_i2c_address`/`switch_to_uart`) and the new `AtlasScientificEZOUart` (serial: writes `cmd\r`, reads CR-terminated lines framed by `*OK`/`*ER`, ignores async status lines, disables the EZO's default once-per-second continuous streaming at startup, and drains stale input before each command so a send-only command's unread `*OK` can't corrupt the next read) - share them instead of each keeping a drifting copy. `AtlasPHSensor` gained a backward-compatible `driver=` injection point (the positional `i2c_bus` path is unchanged). `server.py` selects the transport at startup via `RXN_BENCH_PH_TRANSPORT` (`i2c` default / `uart`, with `RXN_BENCH_PH_SERIAL_PORT` [default `/dev/serial0`] and `RXN_BENCH_PH_BAUD` [default 9600, the EZO UART default]), mirroring the existing `RXN_BENCH_MOCK` env-var pattern. New `MockEZOUart` emulates the EZO serial protocol so the real UART driver stack runs end-to-end in tests, mirroring `MockI2CBus`. Added `pyserial>=3.5` to the `[rpi]` extra (+ `serial.*` to the mypy ignore-missing-imports list). 22 new tests (UART driver protocol/error/timeout handling, mock emulator, sensor injection); all 61 pH tests pass, no existing I2C tests changed. Also tidied `AbstractI2CDriver._read_response` (dropped the never-varied `num_bytes` arg to a `_RESPONSE_NUM_BYTES` constant) so its signature matches the shared mixin's transport hook. Follow-up: the offline Pi bundle must be rebuilt so pyserial is in the wheelhouse before the Pi can run the UART path, and the transport env var must be set on the deployed `rxn-bench-ph` service (e.g. `systemctl edit`) (2026-07-13).
- deployment: document and fix SiLA server discovery failing on the isolated bench network — the frontend's server browser found "0 known devices" even though all three systemd services were healthy and their gRPC ports (`50051`/`50052`/`50053`) were reachable. Two independent root causes, both stemming from `rxnbenchpi`'s intentionally gatewayless instrument network (`docs/rxnbenchpi.md`: no default route by design). (1) The SiLA CDK's mDNS announcer (`sila/framework/discovery/socket.py`) sends multicast via a plain `sendto(224.0.0.251, …)` and relies on the kernel's default-route lookup to choose an egress interface; with no default route that lookup returns `ENETUNREACH`, so every announcement was silently dropped before hitting the wire (`avahi-daemon`'s own records still resolved, because avahi pins the interface). (2) Even once announcements flowed, every server advertised an A record of `127.0.0.1`: `SiLAServerConfig.hostname` defaults to `0.0.0.0`, and the CDK's `find_ip_addresses("0.0.0.0")` auto-detect falls back to loopback here (the Pi's hostname resolves to `127.0.1.1` via `/etc/hosts`, and its `connect(("8.8.8.8", 80))` outward-IP trick can't run without a default route) — so the frontend discovered each server, then probed `127.0.0.1:<port>` (its *own* loopback) and dropped them from the "known" list. Fix has two independent parts: (a) advertised address — pin `sila_server.hostname` to the Pi's bench IP via a `~/.rxn_bench/<device>.json` override (checked ahead of the bundled `configs/<device>.json` by every device `_cli.py`), which fixes the advertised A record and binds gRPC to the reachable interface; (b) multicast egress — an on-link `224.0.0.0/4` route on the bench interface (the CDK's connector never forwards `discovery.network_interfaces` to its multicast socket — it uses the discovery config only as an on/off gate — so `IP_MULTICAST_IF` is never set and that config key is a **no-op**; a route is the only lever, verified empirically by removing it and watching discovery drop). Verified end-to-end: all three advertise `192.168.50.1` over mDNS and answer `Get_ImplementedFeatures` with their `/rxnbench/` features. So a fresh deploy no longer needs the manual step, `install_offline.sh` now auto-detects the host's primary IPv4 (`hostname -I`) and: pins it (forwarding a new `--advertise-ip <IP>` flag to `install_service.sh`, which writes the `hostname` override idempotently — patching an existing override in place or seeding from the bundled config), and, when the multicast group isn't already routable, installs a boot-time `rxn-bench-mcast-route.service` (systemd oneshot: `ip route replace 224.0.0.0/4 dev <iface>`). `--advertise-ip` overrides the detected IP and `--no-pin` skips both (correct on a normal LAN with a default route, where neither problem exists). Because the server now binds a specific interface IP, the device systemd units were changed from `After=network.target` to `Wants=/After=network-online.target` so the address is configured before first start (`Restart=on-failure` remains the backstop). Added a "Discovery on the isolated bench network" section to `docs/deployment.md` (2026-07-13).
- backend: `make start-gantry`/`start-ph`/`start-camera` now work fully offline from inside an extracted `build_offline_bundle.sh` tarball, without ever running `install_service.sh` - fixes `uv run rxn-bench-ph` failing with `Failed to download pluggy==1.6.0`/`iniconfig==2.3.0`/etc. (`Temporary failure in name resolution`) even after the wheelhouse fixes above. Root cause, found the hard way: `uv run`'s implicit project sync resolves against the project's `uv.lock` (which pins each dependency to a specific PyPI URL+hash); in `--offline` mode it only checks uv's own package cache for that pinned entry - `--offline --find-links <wheelhouse>` does *not* substitute in find-links wheels for an already-locked dependency the way `uv pip install --no-index --find-links` does for a plain (non-project) install. An initial attempt using `--offline --find-links` looked like it worked, but that was a false positive from this dev machine's `uv` cache already being warm from earlier unrelated network activity in the same session - retested with `UV_CACHE_DIR` pointed at a genuinely empty directory and it failed immediately. Fixed by having these targets do exactly what `install_service.sh` does under the hood (`uv venv --no-project` + `uv pip install --no-index --find-links <wheelhouse> -e <device>`, bypassing `uv run`'s project/lockfile machinery entirely) and then exec the venv's installed binary directly, only when a `wheelhouse/` is found at the expected offline-bundle location - falls back to the original plain `uv run` for the normal online shared-dev-workspace case. Also fixed a second, pre-existing, unrelated bug this surfaced: `start-ph` never passed `--extra rpi`/`[rpi]`, so `smbus2` was never installed and the real pH server always failed with `RuntimeError: smbus2 is required...` regardless of network - would have broken on genuine Pi hardware even before this fix. Verified with a from-scratch venv (no prior install step) against a native-platform wheelhouse and a cache genuinely emptied via `UV_CACHE_DIR`: all packages install with zero network calls, and the server now runs far enough to hit an actual hardware access error (`/dev/i2c-1`) instead of a packaging error (2026-07-10).
- backend: fix `install_offline.sh`'s vendored-uv path leaving `uv` unusable in the shell that ran it - e.g. `make start-ph` right after a successful install failing with `uv: not found`. Root cause: the offline branch (`export PATH="$HOME/.local/bin:$PATH"`) only mutates that `export`'s own process tree; no script executed as `./install_offline.sh` can reach back into the interactive shell that invoked it, so the change vanished the moment the script exited. The online fallback branch never had this problem since it shells out to the official `astral.sh/uv/install.sh`, which persists PATH into `~/.bashrc` itself - the offline/vendored-binary path (the script's own documented "recommended" mode) never did. Fixed by appending an idempotent PATH export to `~/.bashrc` if `.local/bin` isn't already referenced there (a no-op on stock Raspberry Pi OS, whose default `~/.bashrc` already conditionally adds it - verified with a simulated fresh/re-run/Debian-default `.bashrc` in each of the three states), plus a completion-message note telling the user to `source ~/.bashrc` or open a new shell before running `uv`/`make start-<device>` in the shell they just installed from (2026-07-10).

Added `--exclude='rxnbench/backend/dist'` alongside the script's other dev-cruft excludes. Verified: rebuilt the bundle, confirmed zero `rxnbench/backend/dist` entries in the resulting tarball and a normal ~52MB size (2026-07-10).
- backend: fix `install_service.sh --offline <wheelhouse>` failing on every device with `Failed to resolve requirements from build-system.requires: No solution found when resolving: hatchling` (then `editables` once `hatchling` was added) - offline installs use `uv pip install --no-index --find-links <wheelhouse> -e <device>`, which builds the local package with its build backend; every device's `pyproject.toml` declares `requires = ["hatchling"]`, but `build_offline_bundle.sh`'s `uv export` only captures *runtime* dependencies, never build-system requirements, so `hatchling` (and its own editable-install helper, `editables`) were simply never in the wheelhouse. Fixed by explicitly appending `hatchling`/`editables` to the merged requirements before the `pip download` step, letting pip resolve their own transitive deps (`pathspec`, `pluggy`, `trove-classifiers`) automatically. Verified by extracting a freshly built bundle and running the exact `uv pip install --no-index --find-links ... -e` command `install_service.sh` uses - the editable build now succeeds (2026-07-10).
- camera: new `rxn_bench_camera` SiLA device (TODO-AI.md §2.1, port 50053) - streams a `LatestImage` observable property (SiLA `Binary`/`bytes`) captured from a Crowsnest-managed webcam stream via a plain-HTTP `CrowsnestCamera` driver, with a runtime-adjustable `SetCaptureInterval` command. `CameraProtocol` is a single `capture() -> bytes` method, so Crowsnest is one implementation behind the interface, not the whole abstraction - a future direct-USB or other camera source only needs to satisfy that one method. Every capture is archived to `logs/images/` (7-day retention, shorter than the usual 30-day JSONL default since binary frames are heavier) alongside the standard JSONL event log. Ships a dependency-free mock (`MockCamera`, a placeholder PPM image - no imaging library needed) and a frontend plugin (live image view + interval control). `rxn_bench_client.Camera` adds `snapshot()`/`save_snapshot()`/`set_capture_interval()`. Required the first non-Real/Boolean/SString primitive type: extended `gen_proto.py`/`gen_connections.py` with a generic `Binary` wrapper (`bytes` -> SiLA's native `Binary` basic type, `message Binary { bytes value = 1; }`, matching the CDK's own inline-payload wire encoding for the common case where a captured frame stays under its 2**21-byte binary-transfer threshold). Verified end-to-end against a live mock server (real gRPC subscribe + command call, not just unit tests - decoded image bytes matched `MockCamera`'s output exactly, and an invalid interval was correctly rejected over the wire). Known gap: the real Crowsnest snapshot endpoint (`crowsnest_base_url`/`crowsnest_snapshot_path` in `~/.rxn_bench/machine.yaml`, defaulting to ustreamer's `/snapshot`) hasn't been verified against a live SV08 deployment yet (2026-07-10).

- backend: fix `build_offline_bundle.sh` crashing with `ERROR: Invalid requirement: ...` while downloading wheels. Root cause: `uv export --format requirements-txt` annotates each requirement with `# via <parent>` provenance comments and `--hash` entries, both using backslash line-continuation to span multiple physical lines; the script's `grep -h -v '^-e ' *.txt | sort -u` merge step (to dedupe requirements across the gantry/ph/client exports) sorted those physical lines independently, which shreds the continuation grouping — a `\`-continued requirement line ends up followed by an unrelated sorted line, and pip's requirements-file parser joins them into one garbled, unparseable requirement. Fixed by adding `--no-annotate --no-hashes` to all three `uv export` calls so each requirement is a single plain line (hashes aren't needed here since this file only drives `pip download`, not an installer needing integrity checks) (2026-07-10).
- backend: fix `build_offline_bundle.sh`'s `pip download` failing on every compiled dependency (`ERROR: Could not find a version that satisfies the requirement grpcio==1.81.1 (from versions: none)`, same for lxml/pydantic-core/etc.) once the previous entry's parsing bug was out of the way. Root cause: `pip download --platform linux_aarch64` only matches wheels tagged exactly `linux_aarch64`; compiled aarch64 wheels on PyPI are published under `manylinux2014_aarch64`/`manylinux_2_17_aarch64`-family tags, not the bare `linux_*` family, so every pure-Python wheel (tagged `py3-none-any`) resolved fine while every compiled one silently 404'd. Added a separate `PIP_PLATFORM_TAG` (default `manylinux2014_aarch64`) used only for the `pip download --platform` arg, keeping `PLATFORM_TAG` as the human-readable bundle/directory name so the tarball naming convention documented in `docs/deployment.md` is unchanged. Verified by running the full script end-to-end - all 50 merged requirements downloaded and the bundle tarball built successfully (2026-07-10).

- gantry: non-contact Z-reference calibration option (third slice of TODO-AI.md §1.1) - both the homing dialog and the toolhead calibration wizard can now hover the tip at a known height instead of touching a surface directly, avoiding the risk of driving the tip into the deck or a plate. Homing: if a workspace with a `calibration_reference_well` is loaded, the Z Reference step shows that plate's known top-surface height (`resolve_reference_plate_height()`, new shared helper in `workspace_loader.py`) and confirming calls `set_z(height)` instead of always declaring 0; falls back to the original touch-the-deck flow when no workspace is loaded. `set_z` already existed backend-side (`GantryController.set_z`/`SetZ` SiLA command) but had never been wired into the frontend connection layer - added to `connection_spec.yaml` and regenerated, no backend/proto changes needed.
